## 2026-10-25 17:07-17:11 CORRECTION of the A5 diagnosis (recorder under-count); no code changed yet
The 17:04 entry blamed `rclpy.spin_once` per call. **That was wrong/incomplete.** A persistent `SingleThreadedExecutor` (draft v1) was tested on the live bare sim and still counted 7.2 per row. The recorder uses only 10-18% CPU, so it is not CPU-bound.
- **Actual cause:** the 1/`sample_hz` timer `on_sample` calls `est_pose()` -> `tf_buffer.lookup_transform('map','base_footprint', ..., timeout=0.1 s)` and then a second lookup with timeout 0.05 s, in the recorder's single-threaded executor. When no `map` frame exists (bare responsiveness stack) each sample blocks about 0.15 s, so the executor services about 6.7 timer ticks/s and every subscription (odom, depth, colour) gets the same ~7 per second. On SLAM/AMCL stacks the lookup blocks partially, giving about 27 per second (the 8-9% "image drop" seen in A1/A4b/A6).
- **Verified fix candidate (v2, NOT applied):** put the `on_sample` timer in its own `MutuallyExclusiveCallbackGroup` and spin the node on a `MultiThreadedExecutor(num_threads=2)` so the blocking lookup no longer stalls the subscriptions. Tested on the live bare sim next to an independent counter: recorder counts odom 30.0 / depth 30.3 / colour 30.3 per second (independent counter: 30.0 / 30.3 / 30.3). The lookup logic and timeouts are unchanged, so the estimated-trajectory definition (ATE/RPE) is untouched. Diff: scratchpad `recorder_fix_v2.diff` (37 lines). Observed side effect: a harmless "I/O operation on closed file" message at SIGINT shutdown from a late timer callback; guard would be needed before use.
- Decision still pending with the user (apply v2, or leave and report responsiveness UNMEASURABLE). If applied: unit tests, re-run A5 (bare + loaded) and A6 `avoid_dynamic_cross`, add a pre-registration row, then freeze.
